# Geometry analysis speed — 2026-11-11

Branch `geometry-speed`, from `hardening-2026-11-11` (`e4881d3`).

The instant quote reads an uploaded file in a worker with a 60-second limit. Dense
but ordinary files — a 100,000-triangle print STL, a drawing with a few thousand
lines — ran past it and were sent to a manual quote. The cause was a handful of
loops that compared everything with everything. They have been replaced, and the
condition on the work was that **no result changes**: not a feature count, a DFM
verdict, a gate decision or a price.

## 1. Result

Every result the comparer can check is identical: **214 of the 228 corpus cases
give byte-for-byte the answer of the untouched code** (geometry, DFM for every
process, price and checkout-or-RFQ decision for nine configurations at three
quantities), 5 large curved meshes the untouched code could not finish in the
time available are identical to the first optimised commit, and 9 have no
baseline answer because the untouched code fails or does not finish on them
(§8). No numeric difference was tolerated anywhere. The vetting run is
unchanged (300 quotes, 0 fails, 63 warnings, `results.csv` identical apart from
the quote id).

## 2. How "no result changes" was checked

`tools/geometry-bench/` is the safety net. It was written and its baseline
recorded **before** any analysis code was touched.

- **Corpus** (`corpus.js`, generators in `gen/`): 228 cases, generated at run time
  from seeded generators, so only results are stored. Meshes: UV spheres,
  icospheres, tori, smooth and rough organic blobs, feature plates (through,
  blind, counterbored and countersunk holes, slots, pockets), finely faceted
  plates, pocket grids, embossed and engraved text plates, thin-walled cups and
  vases, stepped shafts, hollow spheres, reliefs, lattices of square and round
  bars, several bodies in one file, intersecting bodies, open spheres and
  sheets, mixed winding, unwelded ("shattered") meshes, random triangle soup
  (local and cube-spanning), non-manifold and T-junction boxes, zero-area and
  duplicate triangles, malformed ASCII, NaN and far-from-origin coordinates —
  at about 1k, 10k, 100k and 500k triangles, as binary STL, ASCII STL and 3MF.
  Drawings: crossing lines, perforated plates (square, hexagonal, tight, as
  block arrays), mixed cutouts (slots, rounded windows, splines, ellipses,
  polygons, keyholes), outlines drawn as loose lines, dense and bulged
  polylines, nested contours, windows, open contours and T-junctions, line
  grids, duplicates and overlaps, scattered rectangles, free splines, inch
  drawings with annotation layers, block inserts, separate parts, self-crossing
  outlines, tight webs, drawings far from the origin and wider than a
  kilometre — from a handful of entities to the 100,000-entity ceiling. Plus
  every CAD file already in the repository: the 17 STL and 8 DXF/STEP vetting
  parts, the STEP fixtures, the IGES and 3MF security fixtures, the 400-hole
  STEP plate and the brand DXFs.
- **Snapshot** (`snapshot.js`): each case is parsed in the production worker
  (`server/parsers/parseWorker.js`, heap ceiling lifted, no time limit) and the
  whole answer is kept as canonical JSON in three sections: *geometry*
  (everything `parseFile()` returns, the preview mesh as a hash, stopwatch
  readings removed), *dfm* (the default DFM, the DFM of every active process and
  a DFM run for nine standard process / material configurations) and *price*
  (the order quote and the checkout-or-RFQ gate for those configurations at
  quantity 1, 10 and 100). Full snapshots of the small and medium cases are
  committed (`baseline/snapshots/`, 2 MB gzipped); the large ones are kept as
  hashes in `baseline/index.json`, with the time and peak memory of every case.
- **Comparer** (`compare.js`): runs the present code over the corpus and fails
  on any difference, printing the JSON path, the baseline value and the present
  value. `check-baseline.js` verifies the recorded baseline is complete and
  that every snapshot hashes to its index entry.
- **Baseline provenance.** Recorded on the untouched code: a second worktree
  of `e4881d3` (`GEOMETRY_BENCH_ROOT=<that checkout> node tools/geometry-bench/snapshot.js …`),
  never on optimised code. The untouched code
  finishes 214 of the 228 cases, some only with the worker's limits lifted (the
  477,480-triangle sphere took 35 minutes of CPU and 68 minutes on the clock).
  Five large curved meshes it could not finish in the time available (a
  478,864-triangle torus was stopped after 40 minutes; the organic blobs are
  three to eight times slower than a sphere of the same size) are compared
  instead with commit `413f781`, the first optimised commit, which changes one
  loop and is itself identical to the untouched code on all 144 small cases, all
  28 medium mesh cases and the ten large mesh cases both could finish, the
  477,480-triangle sphere among them; that reference lives
  in `baseline-step1/` and the comparer marks those cases `identical*`. Nine
  cases have no baseline answer at all (§8).

The comparer ran over the small corpus after every change (it is also in
`npm test`, see §10) and over the medium and large corpus at the points listed
in §5.

## 4. Changes, and why each keeps the result

Each bullet names what a search used to do, what it does now, and the reason the
answer is the same value — not merely close.

### Mesh (`server/geometry/`)

1. **Curved-group pairs** (`regions.js`, `fitGroup`). Was: for every two member
   facets, look the pair up in the adjacency map. Now: walk each member's sorted
   list of higher-numbered neighbours. The pairs come out in the same order
   (lower region, then higher), which matters because the short-arc fit sums
   over them. They and the group's vertex list are now built only if the fit
   reaches the step that reads them (a sphere returns before that).
2. **Region tables** (`regions.js`, `segmentMesh`). Regions, their normals and
   areas, boundary vertices and adjacent pairs are typed arrays instead of an
   object, a triangle list, a Set and a map entry per region. Every sum runs
   over the same items in the same order; boundary vertices are only used for a
   minimum and maximum and for their count; a pair keeps the first longest
   shared edge in (triangle, edge) order, as the single sweep did; union-find
   groups are a partition, which does not depend on the order pairs are united
   in, and groups are still numbered by their lowest region.
3. **Any-hit rays** (`bvh.js`, `occluded`). Tool access, the open-above test of
   a pocket floor and the open side of a half-round channel only ask whether a
   ray is blocked. `raycast()` skips a BVH node for three reasons: the ray
   misses the box, the box is behind the start, or the box starts beyond the
   nearest hit so far. The third needs a hit to exist already, so *whether* a
   hit exists depends only on the first two tests and the triangle test.
   `occluded()` repeats exactly those on the same tree and returns at the first
   hit.
4. **Nearest-hit rays are not reordered** (`bvh.js`, `raycast`). Wall thickness,
   support drop and the inside/outside vote need the nearest hit, and which
   triangle is reported when two are hit at the same distance (a ray through a
   shared edge), or when a box distance and a triangle distance differ in the
   last bit, depends on the visiting order. That order is unchanged; the only
   change is that the traversal stack is no longer allocated per ray. This is
   why lattices are not faster (§8).
5. **Self-intersection test** (`raycasts.js`). Candidates are tested as the box
   query meets them instead of being collected first, with the candidate's edge
   vectors computed once. Same pairs, same order, same arithmetic.
6. **Outline** (`outline.js`). Candidate segments, collinear groups and
   loop-chaining nodes were Map keys made by joining two numbers into a string;
   they are now number pairs in a hash index, with the text path kept for
   non-finite coordinates (the string `"NaN"` equals itself, the number does
   not). Insertion order — which fixes the order of groups, segments and loops —
   is preserved. The coverage grid ("is this point under the projection") lists
   a triangle in the cells, in coarser blocks, or once per row or column,
   whichever takes at most 16 entries, and checks its cell span on lookup: the
   triangles tried for a cell are exactly those that span it, and the answer is
   "any of them", so their order is immaterial.
7. **Shape scoring** (`shape.js`). `scoreRevolved` and the one- and three-axis
   cases of `extentsAlong` are written out per component instead of through
   temporary arrays. Same operations in the same order.
8. **Parser** (`server/parsers/fileParser.js`). A binary STL is read straight
   into flat typed arrays; the row-based parsers (ASCII STL, 3MF, STEP, IGES)
   pack their rows into the same form, and one function, `analyzePackedMesh`,
   does the area / volume / overhang sums with the arithmetic of the row-by-row
   version in the same order. Row input the packer declines (an ASCII STL whose
   facet and vertex counts disagree, a STEP whose bodies only partly carry
   normals) still goes through the old row-by-row code, so it returns — or
   raises — exactly what it did. The normal-bucket count of the legacy estimate
   uses a 9×9×9 table instead of a string key per triangle; only the number of
   buckets of each size is used.

### Drawings (`server/geometry/dxf/`)

9. **Crossings** (`analyze.js`, `crossingsIndexed`). The scan reports, for each
   segment in order, the earlier segments it crosses, in the order of the first
   coarse grid cell the two share (row, then column, then segment number), and
   keeps the first 200. The new search produces that list directly: candidates
   come from a fine grid of conservative segment covers, `properCross()` itself
   decides, hits are sorted by the scan's order, and the search stops at 200
   because nothing after that changes the result. It relies on one fact, proved
   in the code comment: for a drawing up to about 2 km across, `properCross()`
   only reports segments that really intersect (its own tolerance is far above
   the rounding error of its orientation tests), and segments that intersect
   share a cover cell. The indexes are used up to 1 km across (`usable()` in
   `spatial.js`); wider drawings, and any with a non-finite coordinate, use the
   original scan.
10. **Loose ends**: the nearest other end is found by rings of cells instead of
    measuring every end against every other; only ends within the reporting
    distance matter, and on equal distance the earliest end wins, as the scan
    picks.
11. **Containment**: a loop is only examined against larger loops whose
    bounding box holds it; those are looked up on a grid at the loop's centre
    and examined in the original order.
12. **Slot-width and web rays** (`nearestHitIndexed`): candidate loops come
    from a bounding-box grid along the ray's line, and a loop of 400 points or
    more has its own segment index. Loops are still visited in the original
    order through the original bounding-box test against the same running
    minimum; a loop or segment the indexes leave out lies wholly to one side of
    the line, where the ray test returns nothing.
13. **Round-hole webs**: the pair test skips pairs farther apart than the
    narrowest web so far; since that only shrinks, later holes outside a box
    sized by its current value are skipped whatever happens in between, and the
    holes inside are taken in the original order.
14. **Clean-up and chaining**: duplicate detection hashes the eight quantised
    numbers of a primitive instead of formatting them into a string; collinear
    groups are keyed by number and listed in first-seen order; end clustering
    uses a typed hash table. Clusters are a partition (order-free) and nodes
    are numbered by their first end, as before.
15. **Refusal before measuring** (`index.js`): a drawing with more than 5,000
    contours is refused; the count is known as soon as the contours are
    chained, so the measuring that used to precede the refusal is skipped. The
    message and the count in it are the same.

The exhaustive DXF loops are still in the file. They run for drawings outside
the range the indexes are proven for, and `analyseCurves(curves, { exhaustive: true })`
runs them on demand; `speed.test.js` compares exhaustive, default and
forced-index runs on every small drawing.

## 8. What changed in results, what did not finish before, what is still slow

**Tolerated numeric differences: none.** No sum was reordered and no tolerance
was introduced; every compared value is bit-identical.

**Cases where the old code produced no answer.** These are not differences in
an answer, but they are listed because the comparer cannot vouch for them:

- *The old code fails; the new code gives the intended refusal.*
  `dxf-crossing-20k`, `dxf-crossing-50k`, `dxf-crossing-100k`,
  `dxf-perforated-100k` and `dxf-mixed-cutouts-20k` end in "Set maximum size
  exceeded" on the untouched code (after 16–630 s of CPU and 0.7–1.8 GB, limits
  lifted; in the worker they are cut off at 60 s or stopped on memory first). They now get
  "This DXF has N contours — more than the instant quote reads (5,000)…", the
  message the reader already had for such drawings, in 0.2–5 s. The contour
  counts in the message come from the chaining step, whose output is compared
  with the baseline on every drawing the old code does finish.
- *The old code did not finish in 45 minutes.* `dxf-line-grid-223` (a 223 × 223
  grid of separate lines, 99,904 entities): same refusal now, in 0.8 s.
- *The old code fails and the new code fails the same way.*
  `dxf-two-kilometres` (400 large circles on a sheet 2 km wide) is beyond the
  range the indexes are proven for, takes the original path and ends in the
  same "Set maximum size exceeded" (§9, item 3).
- *The old code runs out of memory; the new code runs out of time.*
  `soup-wide-100k` and `soup-wide-500k` (random triangles, each spanning the
  whole bounding cube): the untouched code was stopped by the machine at 4.8 GB
  and 4.7 GB with the heap limit lifted, so in the worker it stops on memory.
  The new code stays at 110 MB of heap for the 100k file and is cut off at 60 s
  with "This model took more than 60 seconds to read…" (both sizes, checked
  through the production pool). The same family at 1,000 and 10,000 triangles
  is identical to the baseline.
- *Compared with commit `413f781` instead of the untouched code* (§2):
  `torus-500k`, `blob-500k`, `roughblob-500k`, `icosphere-328k`,
  `ceiling-sphere-500000`. All five are identical to it.

**Still over the targets.**

- **Lattices of long bars** (`lattice-100k`: 11–12 s of CPU, target 3 s;
  `lattice-500k`: 16 s, target 15 s — it was 26 s and 1.8 GB before, so it
  could not finish inside the worker at all). The time is in rays that find
  nothing in their way: the BVH is split at the median of triangle centroids,
  and two triangles the length of the part per bar face make its boxes overlap,
  so such a ray visits about 1,200 boxes and tests about 950 triangles where a
  sphere's ray visits 40 and 17. A better tree (surface-area heuristic) or
  front-to-back traversal would fix it, and either changes which triangle is
  reported on a tie — so it would not be bit-identical. It needs its own pass
  with a re-recorded baseline and a decision on those ties.
- **Random triangles spanning the whole part** (`soup-wide-100k`: 211 s of CPU;
  it is cut off at 60 s and goes to a manual quote, with 110 MB of heap, where
  the untouched code needs more than 4.8 GB; `soup-wide-500k` is cut off at
  60 s the same way). Every
  box of the BVH is the whole part, so each of the 30,000 nearest-hit rays for
  wall thickness tests all 100,000 triangles. Same remedy and same obstacle as
  above. The file is not a part; a manual quote is the right place for it.
  Local random soup (`soup-500k`, triangles a few millimetres across) finishes
  in 10 s of CPU (34 s on the clock through the production pool on the loaded
  machine) where it needed 17 s and 2.1 GB before.
- **Memory outside the V8 heap.** The worker's 768 MB ceiling is a V8 heap
  limit; typed arrays live outside it and are not bounded by it (true before
  and after). For part-like 500k meshes the whole process peaks at 300–420 MB
  resident. The unwelded extremes are higher: `soup-500k` peaks at about 1.0–1.1
  GB resident for the process (423 MB of it heap; it needed 2.1 GB of heap and
  arrays before and could not finish in the worker), `lattice-500k` at 660 MB.
  If the production machine has less than about 1.5 GB to spare per concurrent
  parse, a 500,000-triangle unwelded soup can still exhaust it; lowering that
  needs the outline and segmentation tables of single-triangle regions to be
  trimmed, which was not done here.
- **STEP** is not faster: 5.8 s against 5.9 s for the 400-hole plate, of which
  about 4 s is OpenCascade tessellating the file (WASM, not ours) and the
  recognition of its 43,000 triangles 1.7 s.
- **Mixed-cutout drawings with thousands of splines** (`dxf-mixed-cutouts-4k`,
  4,001 contours, 300,000 flattened segments): 2.4 s of CPU (6.4 s before),
  9.4 s of wall time through the live server on the loaded machine. It is
  inside the 10-second DXF limit being added on another branch, but not by a
  wide margin when the machine is busy. `dxf-separate-parts-2000` (3.0 s of
  CPU, 5.9 s on the clock) and `dxf-splines-3k` (2.1 s, 6.3 s) are the next
  slowest that are read to the end. `dxf-mixed-cutouts-20k` (20,001 contours,
  1.5 million flattened segments) takes 5.4 s of CPU, 14 s on the clock on the
  loaded machine and 651 MB of heap before it is refused for its contour
  count: under a 10-second limit on a busy machine it would be cut off
  instead, and either way it goes to a manual quote. Every other drawing in
  the corpus, including those at the 100,000-entity ceiling, is under 1.5 s of
  CPU.

## 9. Suspected correctness bugs found and deliberately not fixed

Each is reproduced by the named input and returns today exactly what it
returned before.

1. **A malformed ASCII STL shows the customer a JavaScript error.** An ASCII
   STL with fewer `vertex` lines than three per `facet` makes the parser read
   past its vertex list; the upload answers *"Cannot read properties of
   undefined (reading '0')"* (the parser's message is passed through as
   customer-facing text). Input: corpus case `ascii-missing-vertex`.
   A facet with a fourth vertex (`ascii-extra-vertex`) is accepted, and the
   stray vertex widens the bounding box and the preview while the triangles
   ignore it.
2. **The legacy hole / bend / slot estimate reads a third of the normals of a
   STEP, IGES or 3MF.** `estimateFeatures` loops `i < triangleCount` over
   `normals[i]`, but for those formats `normals` holds one row per *corner*
   (three per triangle), so only the first third of the corner normals is
   counted. It feeds `legacy.estimatedHoles / estimatedSlots / estimatedBends`
   and `estimatedBends`. Input: any STEP, e.g. `fixture-plate_holes-step`.
3. **The old crossing search fails outright on dense drawings.** Once more
   than 2²⁴ segment pairs share a grid cell the pair Set throws *"Set maximum
   size exceeded"* — a `RangeError`, which the upload route reports as "This
   file is damaged or incomplete". Inputs: `dxf-crossing-20k`,
   `dxf-mixed-cutouts-20k`, `dxf-perforated-100k`, and — with only 400 large
   circles — `dxf-two-kilometres`. The new search does not use that Set, so the
   first three now get the intended "more than 5,000 contours" refusal (see §8);
   the last is wider than the indexes are proven for, still takes the old path
   and still fails the same way.
4. **A drawing's contours are measured before it is refused for having too
   many.** Not a wrong result, but the reason a 20,000-hole panel took 44 s to
   be told it has too many holes. Fixed here only in the sense that the count is
   now checked first (§4, item 15).
5. **Ray tests accept numerical noise as a hit when a ray is parallel to what
   it tests.** Both `raySeg` (DXF) and the triangle test in `bvh.js` reject a
   parallel ray with an *absolute* determinant threshold (1e-14); for a segment
   or triangle more than a few tens of millimetres long, rounding noise in an
   exactly parallel configuration can exceed it, and the resulting distance is
   meaningless. Not reproduced with a specific file — it is a reading of the
   code — but it is the reason the DXF ray search and `occluded()` were built
   to test exactly the same candidates as before rather than a geometrically
   equivalent set.
6. **`findCrossings` reports at most 200 crossings but used to keep searching**
   through every remaining pair; harmless except for time (now stops).
7. **Dead values**: the summed shared-edge length of adjacent regions
   (`info.total` in `segmentMesh`) and `endNode` on open DXF chains were
   computed and never read. Both are gone; neither was part of any result.
8. **Test environment**: `server/routes/botCheck.test.js` fails on a fresh
   checkout until `data/rfq-drawings/` exists (it is created by running the
   server); and the health-latency assertion in `server/security/uploads.test.js`
   fails on a busy machine, on the untouched code as well (see §10).
